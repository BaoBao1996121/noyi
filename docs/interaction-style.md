# 对话展示尺度与风格

日期：2026-11-04。状态：设计规范，未实现。

依据：用户本机 Grok Bot 客户端的本地聊天记录（7 个会话、453 条 Agent 文本消息）的结构统计与人工阅读。原始聊天内容私有，不进本仓库；下面只保留统计和我们自己写的规则。

## 1. 观察到的事实

- 对话流里没有任何工具调用、日志或思考过程。记录只有几类条目：双方的文字消息、选项按钮、要密码的表单、附件、执行授权卡片、定时任务变更提示、系统短提示。
- 消息短：中位数约 90 字，三分之一不超过 60 字；超过 300 字的约占两成，基本都是交付结果。
- 一次只说一两句：Agent 连续发言多数是 1–2 条，很少超过 4 条。
- 后台过程只在“有事发生”时浮出来：一句开工回执（“两件事都开始做了，做完一起发你”）、一句结果、或一句卡点（“那台电脑离线，连不上，其他都准备好了”）。
- 说错了直接认：“我之前写的『没有倾斜』是错的，已经改正了”。不辩解，不铺垫。
- 需要决定时给按钮，不让人打字：问题一句话，2–4 个选项，推荐项高亮，危险操作标红；用户回答后按钮收起。
- 自动化的创建、修改、停用以一行灰色事件显示，不占一条消息。
- 后台卡住被系统终止，也只有一行提示，不展开错误栈。
- 实时状态单独有“正在输入”和“正在运行”两个信号。“在干活”靠状态指示，不靠往对话里写进度。

## 2. 我们的规则

### 2.1 什么进对话流

| 进对话流 | 不进（放任务详情，可展开） |
|---|---|
| 开工回执：一句话说做什么、什么时候回来 | 每次工具调用、参数、原始输出 |
| 阶段结果：有用户能用的东西时 | 日志、重试、心跳、内部消息 |
| 卡点：需要用户做什么，其他是否继续 | 模型思考、计划草稿 |
| 最终交付：结论、产物、未解决项 | 成员之间的协调对话 |
| 纠错：之前说错的地方 | “我正在……”这类空进度 |
| 决定按钮、授权卡片、要凭据表单 | 一次能自愈的失败 |
| 一行系统事件：定时任务变了、任务被停了 | 状态变化本身（交给状态指示） |

判断标准：这条消息拿掉后，用户会不会少知道一件需要知道的事。不会，就不发。

### 2.2 怎么说

- 像同事发消息：先说结果或结论，再说必要的原因；一条只讲一件事，宁可分两条短的，也不发一条长的。
- 默认不用标题和加粗。列表只用在并列的数据或结果上。长内容放成文件或附件，对话里只给一句话和链接。
- 数字要实在：“已核对 3 份，还剩 1 份”，前提是真的有这 3 份的记录；不编百分比。
- 不复述用户刚说的话，不说“作为负责人我将”，不在每条结尾加总结。
- 语气跟着用户走：用户随口说“行，你自己搞”，就简短确认后去做。

### 2.3 状态在哪里表达

对话流之外有一条状态栏：“正在处理 / 后台 2 项进行中 / 等你确认 / 已暂停 / 正在停止”，对应 [plan-m0-m1.md](plan-m0-m1.md) 的状态划分。用户想知道细节就点开任务详情，看工具记录和证据。状态变化不发消息，只有落到 2.1 左栏的情况才发。

### 2.4 和机制的对应

- 续接轮次产生的内容同样要过 2.1 的筛选：Worker 交回结果后，总控只在“有阶段结果 / 需要决定 / 最终交付”时才发消息，整合过程不发。
- 投递记录（`messages.kind = delivery`）只存进对话流的内容；工具和日志写进 `operations / evidence`，两者不混。
- 用户在看对话时只更新对话和状态栏，不弹系统通知（plan 第 5 节）。

## 3. 验收要点（未实现）

- 一次含 10 次以上工具调用的任务，对话流里 Agent 消息不超过“回执 + 结果”两到三条，工具记录全部能在任务详情查到。
- 中途一次自愈的失败不产生对话消息；需要用户处理的失败产生一条，说明影响和要用户做什么。
- 需要用户选择时出现按钮，不要求用户手打选项。
- 抽查对话消息：中位长度和“先结论后原因”人工检查，不以字数为唯一标准。
