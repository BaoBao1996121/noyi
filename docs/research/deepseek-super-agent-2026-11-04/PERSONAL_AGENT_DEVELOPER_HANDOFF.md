**目标是让既有 Personal Agent 更可靠地承担持续目标、接住后续输入并减少人的管理负担。继续沿用已有的 Python、asyncio、SQLite、单服务进程、有界并发与一个模型 SDK。**

## 2. 保留的架构决策

以下不是本轮新增发明；如果当前代码已有实现，先验证，再按实际缺口补充。

| 已有决策 | 本轮继续遵守的语义 |
| --- | --- |
| Goal / Task / Run 分开 | 长期目标不会因一次运行返回或一个 Task 完成而自动消失 |
| Evidence / Artifact / Delivery 分开 | 成果验收与消息送达各有结果；发送失败不能重做成功业务 |
| 根任务负责人持续负责 | 委派不转移最终验收责任，不以子 Agent 自报成功替代根任务验收 |
| execution_epoch | 识别当前执行绑定，阻止旧 Worker 回调提交当前结果 |
| requirement_revision | 标识用户要求的版本，旧产物不能覆盖新要求 |
| Artifact base_version | 防止并发修改无意覆盖当前产物；与执行代次不是同一个字段 |
| 取消和暂停有持久事实 | 不把停止请求、执行器已经停止和远端副作用已撤销混为一谈 |
| Inbox / Outbox / effect ledger | 先保存意图，事务提交后执行外部动作，保留未知结果与对账 |
| 合法 wait 不占用持续推理 | 等用户、事件或时间时释放运行资源，不靠反复调用模型保持活跃 |
| 长期记忆有来源、受众、版本与删除 | 聊天历史和摘要不能绕过记忆权限，也不能使删除内容重新生效 |
| Activity / Failure / Progress / Budget 分开 | 没有日志不必然卡死，有日志不必然推进目标；预算耗尽要明确暂停 |
| 每个 actor 的并发和系统总并发有上限 | 人工输入优先不等于同一 Bot 同时启动两个冲突的 Run |

新概念优先扩展现有对象，不同时引入重复的 Ticket、Assignment、Task、Run 四套工作身份。

## 3. 两处命名先统一

**AdmissionPolicy**：新工作能否被接下、推断工作处于 off/observe/auto 哪种模式、依据哪个可信身份与规则版本。它不负责长期目标的时间安排。

**既有 Policy / RoutinePolicy**：保留原先的周期或条件调度职责。不要只因为同名而推翻已有接口；可以先在文档中限定名称，再做必要的局部重命名。

事件来源使用 **EventSourceAdapter**；资料来源描述沿用 **KnowledgeSourceDescriptor**。前者维护事件 ID、原生身份、游标和连接状态，后者描述材料版本、出处、访问与阅读情况。

## 4. 本轮最有价值的四项增量

### 4.1 明确 follow-up 的责任归属

一个 Room 可以有多件工作，一个 Thread 可以涉及多件工作，一个 Task 可以订阅多个 Thread。消息平台的 thread ID 不能直接当 task ID。

先支持一个明确的 follow-up owner 和多个 context 订阅者：

- `own`：把当前授权范围内的人的后续输入交给该任务承担；不等于允许任务执行任意动作。
- `context`：提供受众允许的背景材料；不能产生新的工作授权，也不能仅靠这类输入恢复已取消任务。
- `handback`：当前 owner 判断输入不属于本任务，持久记录交回原因，再进入新工作或其他归属判断。原任务不能一边保留处理责任，一边让另一个任务重复执行同一工作。

订阅扇出与新工作判断分别记录。禁止实现成 `if subscribed: deliver; else: evaluate`：一条 bot/CI 事件可以给现有任务提供上下文，同时触发一个有独立授权依据的新工作评估。只读订阅不能吃掉用户的合法新请求。

主题相似只是证据。优先使用明确 task 引用、reply-to、原消息关联和现有 own 关系；有歧义时可以请求最小补充，也可以留下未归属状态，不必强行猜测。

### 4.2 先确定权限，再判断语义

准入的代码部分确定来源账号、可信操作者、Room 成员关系、当前授权及规则版本；模型部分判断意图、与目标的关系、是否重复、是否有足够实施方向。模型不能从正文中创造新的身份或授权。

建议留存 AdmissionDecision：事件 ID、策略版本、授权引用、决定、依据、observe 的 would_accept 结果。模型评估可能很慢，真正创建 Task 的事务内必须再核对决定依赖的版本是否仍有效。

Observe 用于观察尚未启用执行的新主动推断规则。已有任务的合法后续输入，以及用户已明确允许的周期性或条件性动作，仍按授权执行；不得被一个全局 observe 开关悄悄降为只提建议。是否覆盖下一次 Task，要能追到持续 Goal 的具体授权和预算。

准入检查不是最终动作检查。真正执行外部写入、发消息、修改文件等操作前，工具层还要检查当前身份、动作范围、授权版本、执行代次与资源状态。授权被撤销后，旧 Run 不能继续启动新副作用；已发出的请求则进入对账或补偿，不能宣称已经被撤回。

### 4.3 将“需要人做什么”变成可恢复的状态

复用现有 Approval、wait 和 Delivery，不要求另造独立平台。Attention 至少引用：任务、问题 ID、需要谁回答、对应的 requirement_revision、状态及 resolution。

缺信息、需要新授权、等待结果审阅是三种不同情况。普通信息问题不应该无条件进入权限审批。明确已有授权的动作，也不应因模板统一处理而再次请求确认。

问题更新时使旧问题失效，并撤回尚未送出的旧问题投递。答案绑定原问题与版本；过期回答不得覆盖新要求。重启后已解决的问题不重新询问，未解决的问题有明确等待条件。

### 4.4 人工控制优先，但不突破并发约束

取消、暂停和状态查询由可信事件的轻量路径先受理，不排在长模型任务之后才能入库。执行器在可中断边界检查控制事实；长工具是否能停止，由真实工具能力决定。

可以保留人工优先级或预留容量，但所有路径都受绝对上限约束。同一个 actor 已有 Run 时，输入进入该 Run 的持久队列，或结束后再调度，不能为了“快速响应”产生两个互相覆盖的执行器。

## 5. 最小数据变化建议

这是一份语义契约，不是必须照抄的数据库 schema。先找当前对象和表，再决定增加字段还是增加关系表。

| 关系 | 建议保存的信息 | 需要保护的不变量 |
| --- | --- | --- |
| ThreadSubscription | task_id、source/account/thread、own/context、active、audience_ref | 背景可见不等于获准执行 |
| FollowupDisposition | event_id、owner_task_id、状态、交回理由、相关版本 | 重启后知道谁仍承担该输入 |
| AdmissionDecision | event_id、policy_revision、authority_ref、决定、依据 | 过期评估不能提交新工作 |
| Authority 引用 | 可信主体、原授权、动作/对象/范围、版本、撤销事实 | 输入消息不能提升原有权限 |
| Attention | task_id、question_id、目标答复者、要求版本、状态、答案 | 已回答不重复问，过期回答不误恢复 |

为现有历史消息补关系时，不把“出现在同一 Thread”批量迁移成工作授权。旧记录如果不能确定 owner，就保留未归属或需重新判断的状态；迁移过程应可重跑且不产生外部动作。

任务输入至少区别“已持久保存”“已进入某次模型请求”“处理责任已完成”。在进程队列中成功 put，或者模型已经看过一遍，都不能自动代表用户的要求已落实。

## 6. 按当前进度选择实施切片

### 如果 M0 尚未闭环

先完成一个 Bot、一个真实模型 SDK、少量实际工具、持久 Task、真实产物和根要求验收。只预留事件来源、任务 ID 和版本位置。本轮研究不能变成推迟第一项实际交付的理由。

### 如果 M0 已经完成

优先做 **M1：同一 Bot 交错处理两项任务，并接住正确的后续输入**。推荐切成四个可审查提交：

| 切片 | 修改范围 | 完成的实际证据 |
| --- | --- | --- |
| A：任务与输入关系 | 在现有 inbox 增加 own/context 与 disposition；支持明确引用 | 两个任务的交错输入不串单，重复事件不重复执行 |
| B：改变与交回 | 原任务更新要求版本，超范围输入持久 handback | 旧结果不能覆盖新要求，越界输入不会偷偷扩权 |
| C：问题与等待 | 复用 Approval/wait，保存问题版本与答案 | 问题答完后重启不重问；过期答案不恢复错误任务 |
| D：人工控制 | 轻量控制入库、运行边界检查、优先调度 | 并发满时仍可取消，且不启动同 actor 的并行 Run |

如果代码已有某个切片，则补充缺少的关键测试或直接进入下一个未通过切片，不换名重写。

### 后续仍沿 M2 至 M5

- **M2，Worker：**沿用同一输入协议；检查旧执行代次、子任务结果、交接恢复。根任务负责人继续验收。
- **M3，自由 Bot / Room / Team：**用户可直达任意 Bot；共享路由实现但不共享越权记忆。跨渠道身份必须有确定的绑定依据。
- **M4，持续 Goal / 触发：**游标、事件去重、AdmissionPolicy、规则级 observe→auto、暂停和恢复。已授权的持续动作与新推断规则分开。
- **M5，复盘和自用：**用实际成果、人工管理时间、总费用、误触发与无声停滞评估效果，增加独立进程健康检查。

不增加默认 Temporal、分布式队列、全局角色树、向量平台或云端弹性调度。遇到真实瓶颈再决策。

## 7. 三类“结束后收到消息”要分别实现

| 当前状态与输入 | 必须明确的行为 |
| --- | --- |
| 正常完成，收到“谢谢”或旧事件 | 不重新执行，不为闲聊创建重复任务 |
| 正常完成，收到授权范围内的有效补充 | 当前授权下续做，或新建关联任务；保存决定，不丢请求 |
| 暂停，收到旧事件或旧回调 | 继续暂停；按已定义、可核验的恢复条件或显式恢复指令处理 |
| 明确取消，收到旧事件、CI 或旧 Worker 结果 | 保留取消事实，不自动复活；需要新的有效授权才能继续相关工作 |

正常完成后的续做策略可以由当前产品选择，但不能同时走“恢复原任务”和“创建新任务”而重复执行。恢复时需要新的有效执行绑定；取消、授权和要求版本的旧检查结果不能直接复用。

## 8. 验收必须区分已运行和待运行

[acceptance_cases.json](acceptance_cases.json) 是本次提供的场景规格，所有场景均标为 `specified_not_run`。它们不是可直接运行的测试程序，也不证明当前产品已满足要求。

选择当前切片相关场景，改写为真实产品代码上的测试。要保留三类证据：

1. **确定性协议测试**：真实路由、账本、事务与恢复代码；可使用模型替身、假渠道和故障注入，重点检查持久状态与外部动作计数。
2. **真实模型任务**：同一 Bot 中交错发送任务 A/B 的补充、越界请求、材料更新和取消，检查模型语义判断与实际成果质量。
3. **真实渠道和持续使用**：真实身份字段、游标分页、断连恢复、回声去重、投递与连续运行。没有接入时明确标未运行。

同一逻辑外部操作在远端已成功而本地回执丢失时，应复用幂等键、读回对账或保留 unknown。测试不能通过“换一个 tool_call_id 再调用一次”来伪装恢复成功。

除了结果是否完成，还记录归属错误、重复工作、人工控制延迟、主动误触发、总成本和用户接管次数。权限/受众违规不能用较高平均成功率抵消；性能阈值从本项目模型和渠道基线建立。

## 9. 别照搬的上游前提

| 上游前提或边界 | 我们的处理 |
| --- | --- |
| 一个仓库和一个服务身份 | 保留多长期 Bot、私聊、Room 与 Goal owner |
| 跨平台人物对应可以放在提示材料 | 用可核验账号绑定和存储/工具 ACL |
| Mandate.scope 是范围文本 | 记录授权依据，同时在动作入口执行确定性限制 |
| OS 用户权限下执行 shell，独立目录不是沙箱 | 工具隔离按能力配置；不能用 prompt 代替安全边界 |
| 活跃 Ticket 遇 policy change 主要收到通知 | 用户明确撤权须阻止旧 Run 新增副作用 |
| PR 跟踪决定部分完成语义 | 使用我们的根任务验收和 Goal 退出条件 |
| 上游 memory.ts 是测试内存 Repository | 继续建设有来源、受众、版本、纠正和删除的个人记忆 |
| 记录尚无整体清理机制 | 定义保留与删除；同时保留必要防重/对账依据 |
| 文章有云弹性、BYOM、Watchdog 探索 | 不当成已交付能力或当前必须引入的组件 |

出处逐条见配套报告的官方文档与固定 commit 源码链接。文章的合成负载实验没有验证我们的真实任务质量、成本、长期稳定性或上线速度。
