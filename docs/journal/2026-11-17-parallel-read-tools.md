# 一轮里的多个只读工具改成同时执行：调研任务总耗时少四分之一

- 日期：2026-11-17
- 类型：优化
- 相关提交：（见本篇所在提交）

## 问题

上午的 PTC 测量（[ptc-measurement.md](../validation/ptc-measurement.md)）发现：模型已经有 45% 的轮次一次发出多个工具调用，比如同时打开三个搜索结果，但执行层是一个接一个地跑。网页读取单次要 0.7～29 秒，串行时一轮要等所有页面的耗时之和。用户在决策卡片上同意先做这一步。

## 前后对比

同一份代码，改前组把所有工具的「可并行」声明关掉（等同原来全串行），改后组按声明执行。真实 DeepSeek flash 加 DeepSeek 搜索和读页，经完整服务和 Pi 执行循环跑 3 道多步调研题（两种饮食的适用人群与禁忌、编程语言新版本特性、数据库分词器差别），每题每组 2 次，并发 2。

| 指标（6 次合计） | 改前 | 改后 |
|---|---|---|
| 验收通过 | 6/6 | 6/6 |
| 总耗时 | 420 秒 | 315 秒（-25%） |
| 工具阶段耗时（每轮从第一个工具开始到最后一个结束） | 127 秒 | 81 秒 |
| 工具阶段 ÷ 工具耗时之和 | 1.00 | 0.74 |
| 模型轮数 | 59 | 49 |
| 输入 token | 117 万 | 95 万 |

读法：

- 工具阶段 ÷ 耗时之和从 1.00 降到 0.74，这是并行本身的作用，不受模型发挥影响。
- 总耗时少的 105 秒里，约 46 秒来自并行；其余来自改后组恰好少走了 10 轮（模型每次的走法有波动），不应全算作并行的功劳。保守地说，并行本身省总耗时约 11%，和上午测量时估的 12% 一致。
- 时间用多少，主要看这一轮里最慢的那一页。读到一个要等 28 秒的页面时，并行能把同一轮其他页面的时间藏在它后面。

真实服务验证：重启本机服务后，从本机页面发了一条技术调研消息（数据库分词器差别，不含自用库内容）。6 轮、12 次工具调用，验收通过，用时 77 秒。其中一轮同时读三个页面：一个页面要等 28 秒，另外两个在它等待时已经读完。

## 怎么做的

- **由工具定义决定能否并行。** `ToolSpec` 加了一个 `concurrent` 属性。插件注册时检查：只有没有副作用的读工具（`effect="read"`、不独占、不只用于展示）才能声明并行，声明错了就拒绝注册。目前声明并行的有：搜索、读网页、读资料、读成果、读记忆、读子任务结果、读依赖、读审阅证据。写成果、提交验收、更新计划（只用于展示）以及一切有副作用的工具都保持串行。
- **桥接层只认这个属性。** 运行时把 `concurrent: true` 附在交给执行层的工具定义上，桥接据此把工具设成 Pi 的 `parallel` 或 `sequential`。整体开关改成 `parallel`。Pi 自己的规则是：一轮里只要有一个串行工具，整轮串行。交给模型的工具定义不带这个字段。
- **宿主端能同时应答多个请求。** 原来 Python 端读一条请求、处理完、再读下一条，Pi 并行发出来的请求也会被它排成串行。现在每个请求单独起一个任务处理，处理完各自回写；任何一个出错就关闭会话，并把错误抛出来。
- **账本并发写入安全。** 所有工具调用都在同一个事件循环里，SQLite 事务是同步执行的，没有一处事务跨过 `await`（用语法树检查过）。所以两次调用的账本写入不会交错。
- **搜索预算不会超。** 预算的计数和扣减发生在搜索的第一个 `await` 之前，同一循环内不会被别的调用插队。测试里一轮并发 4 次搜索、预算 2，结果正好 2 次成功、2 次被拒。
- **快照和逐字核对不受影响。** 同一页面或同一份资料的第一次读取会写下快照，引用核对要对得上这一版。新增了按快照文件加锁：同一轮读同一页两次时，只真正抓取一次，第二次读同一份快照，两次回执的摘要相同，逐字核对照常通过。

先写失败的测试（同一轮两个读页调用是串行的），改完后转绿。另加了几条测试：有副作用的工具让整轮保持顺序；并发搜索不超预算；同页并发只抓一次且引用核对通过；插件不能给写工具声明并行；交给执行层的工具定义带并行标记，交给模型的不带。

## 没做到 / 边界

- 并行的收益取决于模型一轮发几个调用。真实服务那次的 4 个读页轮次里，3 个轮次的页面命中缓存，只要 0.01 秒，所以只有 1 轮看得出并行。
- 只读工具之间仍有一点共享状态：搜索预算、快照文件。都按上面的方式处理了。以后新增声明并行的工具，也要满足「不写外部状态」这一条。
- 全量测试里有一条计时测试偶发失败：它给了 1 秒预算，而 Pi 子进程冷启动要 0.3～1 秒。改前代码在同一台机器上也会失败（交替对照，各 12 次里各 5 次没走到读取），与本次改动无关。顺手把它的预算放宽到 3 秒，6 次全过。

## 写文章可用的点

「让 Agent 更快」的第一步不一定是换模型或换架构。模型早就一次发了三个读页请求，是执行层一个个排队在跑。只要让「能不能并行」由工具自己声明，而不是在执行层按工具名列白名单，再把账本、预算、快照这三处共享状态逐一核对清楚，就能拿到这部分收益。
