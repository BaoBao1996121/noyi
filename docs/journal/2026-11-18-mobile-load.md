# 手机在外面打开 Noyi：再次打开从 3.7 秒降到 0.7 秒，只发 1 个请求

- 日期：2026-11-18
- 类型：优化
- 相关提交：（见本篇所在提交）

## 问题

家里电脑装好 Noyi 后，iPhone 经 Tailscale 访问。连家里 Wi-Fi 时很流畅；人出门走 5G，打开要很久，屏幕上只有标题栏和空白，顶部加载条停在约 10%。

本机查下来，原因都在「每个请求都很贵」的场景下被放大了：

- 所有页面和静态文件都是 `Cache-Control: no-store`，而且不压缩。每次打开都要把约 200 KB 的脚本和样式重新下载一遍。
- 脚本按 ES 模块一层层导入：先下 `app.js`，读完才知道要下 `goals.js` 等，再下一层的 `reviews.js`。每一层多一次往返。
- 脚本全部到齐后才请求 `/api/bootstrap`，它回来后才请求 `/api/state`（约 130 KB，压缩后 22 KB）。
- Service Worker 只缓存了 3 个样式文件和一个图标。

局域网里往返不到 1 毫秒，这些都无所谓；外网每次往返几百毫秒，就叠成了几秒。

## 前后对比

测量口径：`scripts/measure-mobile-load.py`。本机起一个后台服务关闭的 Noyi（用真实库的副本，8 件事、21 条消息、29 条回复、34 条记忆），前面加一个节流代理：每个请求加 300 毫秒往返，所有请求共用一条 2 Mbps 的链路。Chromium 手机视口经代理打开页面，计时到对话里出现第一条消息为止。冷启动是全新浏览器第一次打开；热启动是同一浏览器关掉页面后再打开。各测 3 次取中位数。

| 指标（往返 300 毫秒、2 Mbps） | 改前 | 改后 |
|---|---|---|
| 冷启动：出现对话 | 4.26 秒 | 1.99 秒 |
| 冷启动：首屏前的请求数 | 24 | 14（另有 5 个在对话出现后才发） |
| 冷启动：传输字节 | 354 KB | 97 KB |
| 热启动：出现对话 | 3.73 秒 | 0.73 秒 |
| 热启动：请求数 | 17 | 1 |
| 热启动：传输字节 | 304 KB | 22 KB |

把往返加到 800 毫秒、带宽降到 1 Mbps（模拟 Tailscale 走中转），各测 1 次：

| 指标（往返 800 毫秒、1 Mbps） | 改前 | 改后 |
|---|---|---|
| 冷启动：出现对话 | 9.16 秒 | 4.47 秒 |
| 热启动：出现对话 | 7.94 秒 | 1.40 秒 |

热启动是平时最常见的情况（主屏幕图标点开），它现在只剩一次往返加上 22 KB 的页面。

## 怎么做的

根因是一类问题：**启动所需的请求是串行的，而且每次都从零开始**。往返越贵，这种结构越慢。修法按这个来，不针对某个文件：

- **静态文件按构建版本长期缓存。** 服务启动时把所有静态文件算一个总哈希作为构建版本，服务端在页面、模块导入语句、manifest 和 Service Worker 的列表里，把每个 `/assets/x` 都改写成 `/assets/x?v=<版本>`。带当前版本的请求返回 `max-age=1 年, immutable`；其他请求和页面本身都用 ETag 加 `no-cache` 重新验证，没变就回 304。发新版本时任何一个文件变了，版本就变，所有地址跟着变，手机不可能继续用旧脚本。导入语句也带版本，所以子模块不会被旧缓存卡住。
- **文本按 Accept-Encoding 压缩。** 静态文件启动时预先 gzip 好；1 KB 以上的 JSON 响应也压缩。`/api/state` 从 130 KB 变成 22 KB。
- **页面直接带上首屏数据。** 首页由服务端拼出来，`/api/bootstrap` 和当前房间的 `/api/state` 的结果放进一个 `<script type="application/json">` 数据块，页面拿来直接画。这样少了两次串行往返。数据块里所有 `<` 都写成 JSON 转义（反斜杠 u003c），消息内容关不掉这个块。房间号由页面写进 cookie，只是偏好，服务端照常校验归属，不认识就退回默认房间。带数据的页面是 `no-store`，与接口一样不进缓存。
- **模块一次全要。** 服务端把页面入口脚本的整个静态导入树写成 `modulepreload`，浏览器一次并发下载，不再一层一层发现。
- **非首屏模块推迟加载。** 账本回放、像素画风、记忆星系（共约 57 KB）改成第一次打开对应标签时才 `import()`。
- **Service Worker 缓存整个应用外壳。** 列表由服务端按当前构建生成（所有 js 和 css，带版本号）。接口和页面都不经它缓存，所以手机上不会显示过期的对话；新构建有新的缓存名，激活时删掉旧缓存。

比较过的方案：

- 只做 ETag + `no-cache`：实现最简单，但热启动仍要为每个文件付一次往返（17 次 304），在 800 毫秒往返下仍要好几秒。所以用了版本号 + 长期缓存，ETag 只留给页面和不带版本的请求。
- 先出一个很小的启动脚本，让它提前发两个接口请求：实测冷启动只快了约 0.2 秒，因为它本身也要等一次往返才能下载。改成页面直接带数据，省掉的是整整两次往返。
- 把所有脚本打包成一个文件：要引入构建工具，和仓库「不加构建步骤」的现状冲突；`modulepreload` 已经把层数压成一层，收益差别不大。

不变的部分：配对和身份校验（`remote_hosts`、Tailscale 账号、设备 cookie）都在中间件里先跑，首页带数据也在校验之后；未配对的手机拿到的仍是配对页。长轮询、「看到才算送达」、流式草稿、推送都没改。两份静态文件白名单的测试改成也检查 `import()`，推迟加载的模块漏进白名单时同样会被抓到。

性能测试 `tests/test_mobile_load.py`：按真实库 3 倍的数据造账本，断言首屏请求数与数据量无关、页面自带首屏数据（不需要接口往返）、所有导入的模块都被预加载、回放和星系不在首屏；第二次打开所有静态文件都能 304 或直接用缓存；改一个文件后所有地址和 Service Worker 都换版本。耗时只留 10 秒的宽松上限。

发布后「刷新使用新版」（就是一次普通刷新）在真实浏览器里实测过：页面先由 Service Worker 接管，然后在磁盘上改一个 js 和一个 css，刷新一次。新脚本立刻运行，新样式立刻生效，旧构建的缓存被删掉，只剩新构建的缓存。

## 没做到 / 边界

- 冷启动仍要约 2 秒（300 毫秒往返）：页面一次、样式和脚本一次，再加上浏览器的连接建立。再往下要靠 HTTP/2 推送或内联关键样式，收益有限，没做。
- 如果 Tailscale 走中转（DERP），每次往返本身就更长。代码能做的是把往返次数压到最少：热启动已经是 1 次。剩下的时间就是这一次往返加 22 KB 下载，取决于网络本身。
- 手机上的真实表现还没测，以上数字都来自本机模拟。

## 写文章可用的点

弱网下决定速度的往往不是字节数，而是串行往返的次数。把「几层一个等一个」压成「一次」，比把文件压小更管用；而带版本号的长期缓存让第二次打开几乎不用联网。
