# 用现成的 QuickJS 沙箱重做“让模型写代码调工具”：代码全跑通了，但答案没交出来

- 日期：2026-11-18
- 类型：阶段收口（实验，未改产品代码）
- 相关提交：（见本篇所在提交）

## 问题

11-17 自己写了个 Python 沙箱做 PTC（让模型写一段代码批量调只读工具）原型，头三批全败在沙箱本身。后来查到 Pi 生态有现成的 `@earendil-works/pi-codemode`：QuickJS 编成 WASM，每次执行一个 worker 线程，死循环、内存超限、禁用 API 都能拦住。这次用它再做一次小实验，按开跑前写定的门槛决定上不上产品。

## 前后对比

口径：同上次的 3 道题（多来源对照调研、版本发布事实、技术文档对比），每组每题 5 次，共 45 次任务。DeepSeek flash，effort medium；任务预算模型 24 次、工具 60 次；全部经 Service + Pi 完整执行循环，含写报告和引文核对验收。访问线上并发 2。

- A 逐步调用：现状，web_search + fetch_page，只读工具同一轮并行。
- B 批量读页：已搁置的 read_pages 实验代码（exp/read-pages 0770464），6 次复用上次同提交、同脚本的结果，补跑 9 次。
- C codemode：模型只看到一个 `codemode` 工具，在 JS 里调 `tools.web_search` / `tools.fetch_page`。嵌套调用走产品真实的工具入口，预算、操作记录、引文核对照常生效。沙箱 timeout 60 秒、内存 64 MB，工具声明由 `renderDeclarations()` 生成，提示词固定并记了哈希。

| 指标 | A 逐步调用 | B 批量读页 | C codemode |
|---|---|---|---|
| 验收通过 | 15/15 | 15/15 | **11/15**（4 次工具预算用完） |
| 代码执行跑通 | — | — | **102/102** |
| 盲评均分（满分 20，未交付按最低分） | 18.4 | 18.3 | **14.7** |
| 只看已交付的盲评均分 | 18.4 | 18.3 | 18.6 |
| 输入 token 合计 | 274 万 | 340 万 | 225 万 |

最难的一题（多来源对照）差别最大：C 组 5 次只交付 2 次，读页 21～39 次（A 组 17～25 次）。另外两题 C 组 9/10 交付，质量与 A 组持平。

门槛判定（开跑前写定）：

| 门槛 | 结果 | 是否通过 |
|---|---|---|
| 一次跑通率 ≥ 80% | 102 次执行全部跑通，每次任务的第一段程序也都跑通 | 通过 |
| 质量不低于逐步调用组（容差 0.5） | 14.7 对 18.4 | **不通过** |
| 比批量读页组再省 ≥ 20% 输入 token | 省 34%（对逐步调用组只省 18%） | 通过 |

结论：**维持现状，不上 codemode**。

## 怎么做的

- 一个 Node 小脚本只管跑 `CodemodeSandbox`。脚本里每次工具调用都发回 Python，由 `runtime.execute_tool` 执行。所以嵌套调用和普通调用走同一条权限、预算、记录、引文核对的路，实验里没有另造一套工具。
- 失败分类按 sandbox 返回的错误种类加错误信息判定：语法、用了不存在的 API、工具报错、超时、沙箱。这次没有一次落到前四类：模型没写过 `require`、`fetch`、`setTimeout`，也没有语法错。上次 Python 沙箱的问题（import 白名单、`asyncio.run` 嵌套）换成 JS 之后自然消失了。
- 冒烟时发现一处口径问题：产品按“每次工具调用有没有新进展”计停滞，一段程序重读已缓存的页面会被逐次累计，任务很快被判“卡住”。实验里改成一次 codemode 调用算一次活动，只要程序里有一次新进展就算进展。工具预算仍按每次嵌套调用扣，与产品一致。
- 盲评：每题 15 份报告打乱，Claude Opus 5.5 按正确、完整、有据、条理各 1～5 分打分，换两种顺序各评一次取平均，评审不知道组别。

## 没做到 / 边界

- 失败的根因不在沙箱，在“代码里调工具太便宜”。把工具调用挪进代码后，模型不再为每次读页付上下文代价，于是读得更多、更散：冒烟时见过一段程序把同一个长页面按偏移量一次拉 15 段；多来源题平均 24 次搜索和读页，撞上每任务 60 次的工具预算。多出来的读页大多是重复读：同一任务里再读同一页同一段走本地缓存，不再请求读页服务，只是白扣工具额度。（补跑一节有逐条核对的数字。）
- 只看交付了的报告，C 组质量不差（18.6）。所以这是“能不能稳定交出来”的问题，不是“写得好不好”的问题。
- 省 token 的账也要打折扣：C 组相对现状只省 18%，耗时反而多 25%。工具调用次数翻倍，但真正多花钱的是搜索：按次计费，全量里 C 组平均每任务 3.3 次，A 组 1.5 次。
- 每组每题 5 次，样本仍小；只有 3 道题，跨题差异比组间差异大。

## 写文章可用的点

沙箱从“自己写”换成“现成的 QuickJS”，代码跑通率从 6 次里 5 次涨到 102 次全过，执行环境这块确实不再是问题。真正卡住的是激励：一次读页不再占上下文，模型就不再节制，把预算花在重复读页上。PTC 省下的 token，有一部分会被更多的工具调用吃回去。

## 补跑：放宽工具额度

目的：确认 codemode 组在多来源对照题上没交付，只是因为每个任务 60 次的工具额度。

口径：只跑 codemode 组的这一题，5 次。唯一的改动是每任务工具额度从 60 次改成 120 次。模型预算（24 次）、提示词（sha256 `aa9e8b2a…`）、沙箱参数（60 秒、64 MB）、停滞计法（一次 codemode 调用算一次活动）、并发 2 都和全量一致。判定在开跑前写定：交付 ≥ 4/5，且已交付报告的盲评不低于逐步调用组同题。盲评把这 5 份和逐步调用组同题的 5 份打乱一起评，两种顺序各评一次取平均。逐步调用组的分数用同批重评的结果，因为跨批次的分数不可比；它在全量那次是 17.0。

| 指标（多来源对照题，各 5 次） | 逐步调用 | codemode，额度 60 | codemode，额度 120 |
|---|---|---|---|
| 交付 | 5/5 | 2/5 | **5/5** |
| 盲评均分（满分 20） | 17.6（全量那次 17.0） | 9.0（未交付按最低分） | **17.8** |
| 平均输入 token | 39.0 万 | 26.8 万 | 22.2 万 |
| 平均耗时 | 128.9 秒 | 158.7 秒 | 114.9 秒 |
| 平均搜索 + 读页次数 | 23.6 | 40.4 | 34.6 |
| 每任务工具调用总数 | 26～32 | 35～62 | 27～88 |
| 代码执行跑通 | — | 58/58 | 42/42 |

判定：交付 5/5，盲评 17.8 不低于 17.6，**原因确认是工具额度**。额度放宽后，这道题上 codemode 比逐步调用少 43% 输入 token，快 11%，质量持平。

对主结论的影响：按原门槛判定的“维持现状”不变，因为全量是在产品现行额度下测的。但不过线的原因已经查清，不是模型写代码的能力，也不是答案质量，而是工具额度的计法。逐条核对这道题的读页记录：

- 多出的调用大多是重复读。codemode 额度 120 的 5 次里，平均每次有 9 次是把同一页同一段再读一遍，逐步调用组不到 2 次。产品第一次读完就把页面存成本地快照，同一任务里再读直接从快照拿，不再请求读页服务，不额外花钱，只是白扣工具额度。重复读的原因是程序只把筛过的片段交回模型，片段不够时模型就再写一段程序、换个关键词把同几页重读一遍。
- 按不同网页算，codemode 平均每次读 11.8 页，逐步调用组 9.4 页，只多 26%。
- 真正多花钱的是搜索：平均每任务 6.8 次，逐步调用组 2.8 次。

所以要上产品，该改的是额度计法：同一任务里命中已存快照的重复读不扣额度，靠停滞计数和沙箱超时防止无限循环。不需要给嵌套调用单独设额度。那次 88 次工具调用的个例里，有 26 次是一模一样的重复读。其余两题没有在额度 120 下补跑，所以“全面不低于现状”还没验证。
