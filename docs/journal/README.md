# 开发日志（写文章的素材库）

每完成一个需求点（一个功能、一次优化、一次修复、一个阶段收口），就在这里留一篇。目的：以后写技术文章或博客时直接取材，不用回头翻提交记录和聊天记录。

## 什么时候写

- 一个需求点做完并验证过，就在**同一次提交**里写好它的日志。没验证的不写结论，只写「待验证」。
- 一次改动只是小修补、属于某个已有需求点，就补进那篇，不另开新篇。
- 做到一半被推翻或搁置的也写，写清楚为什么停。这类素材写文章时往往最有用。

## 文件名

`YYYY-MM-DD-简短英文名.md`，例如 `2026-11-16-first-reply-latency.md`。日期用完成那天。

## 模板

```markdown
# 标题：一句话说清做成了什么

- 日期：YYYY-MM-DD
- 类型：功能 / 优化 / 修复 / 阶段收口
- 相关提交：（简短哈希，可多个）

## 问题
用户遇到了什么、原话是什么（去掉隐私）、为什么值得做。

## 前后对比
有数字就写数字，写清测量口径（测了几次、什么条件、怎么算的）。

| 指标 | 改前 | 改后 |
|---|---|---|

没有数字的写体验对比：改前用户看到什么、改后看到什么，能配演示库截图就配。

## 怎么做的
大致思路，不贴大段代码：
- 根因是什么，属于哪一类问题；
- 在哪一层修，用的通用规则是什么（说明为什么不是只对这个例子的特判）；
- 比较过哪些方案，为什么选这个。

## 没做到 / 边界
还没解决的、刻意不做的、已知限制。

## 写文章可用的点
一两句：这件事里最值得讲给别人听的地方。
```

## 隐私规则（仓库是公开的）

- 不写健康数据（体重、饮食、照片内容），不写公司信息，不贴自用库里的原始对话。
- 用户原话只在去掉隐私后引用；截图一律用演示库（`scripts/demo-replay.py`）。
- 不写密钥、本机绝对路径、内部账号。
