# 快了以后答得够不够好：回复层要不要开思考的对比评测

- 日期：2026-11-17
- 类型：阶段收口（评测，未改产品行为）
- 相关提交：（见本篇所在提交）

## 问题

上一步把首句回复压到中位 1.4 秒、流式首字 0.86 秒，用的是回复层不开思考。用户随后说：「现在的回答确实很快了，但是我又开始担心质量是否合格，是不是真的思考了。」他设想的体验是：「像一个可靠的助手一样，我说个任务，他会先答应一下，然后去做」，难题交给做事层开思考，或者让回复层自己判断要不要细想。

在改之前，要先知道不开思考到底差在哪类题上，差多少。

## 前后对比

22 道题（9 条自用库里的真实消息，13 条同领域补题），每题三种答法各跑 2 次，Claude Opus 5.5 盲评，满分 20。

| | A 现状（不开思考） | B 回复层开思考 | C 先回执再交执行层细想 |
|---|---|---|---|
| 首字中位 | 0.94 秒 | 4.83 秒 | 0.94 秒 |
| 完整答复中位 | 2.6 秒 | 6.7 秒 | 8.6 秒 |
| 质量总分 | 16.7 | 17.1 | 15.4 |
| 计算题正确分（满分 5） | 3.0 | 3.8 | 3.5 |
| 闲聊总分 | 19.2 | 19.7 | 12.5 |

回复层自己判断「简单 / 细想」，22 题判对 17 题，单次判断 0.8 秒。按判断分流（简单题走 A，细想的走 C），均分 17.2，和全开思考持平，首字保持 0.9 秒。

完整数字和读法见 [docs/validation/thinking-mode-eval.md](../validation/thinking-mode-eval.md)。

## 怎么做的

- **复用产品本身的提示词和协议。** 评测脚本直接导入产品的接收提示词、决定工具定义和流式草稿解析，上下文按产品的格式拼：前文、已确认的记忆、Bot 角色、执行层能力。测出来的就是产品在用的那条路，不是另写的简化版。
- **题目不进仓库。** 自用库里有健康和公司信息，题目、回答和抽查清单都放在本机不进 Git 的目录，仓库里只有类别、改写后的示例和统计。
- **盲评要把产品形态交代清楚。** 第一轮评审没给当前时间，也没标出哪部分是回执、哪部分是成果，结果「今天」被判成编造，回执被当成答复的一部分扣分。补上时间、把两条消息分开显示之后重评，C 的分数从 14.8 回到 15.4，A、B 基本不变。教训：评审看到的信息要和用户看到的一样，否则扣的是评测设置的分。
- **「需要细想」用结果定义。** 不预先给题目贴难度标签，而是看开思考的答法是否比不开思考的平均高 1 分以上，或不开思考的答案出过正确分低于 3 的错。路由判断再拿去和它对照。

## 没做到 / 边界

- 样本小，差 1 分以内的结论不可靠。能站得住的只有两条：计算题不开思考会算错；闲聊和简单事实走「先回执再细想」会明显变差。
- C 的执行层是近似实现：单轮、无工具、纯文本，没走产品里写文档和验收的流程，真实情况会更慢。
- 回复层直接开思考（B）测出两个问题：DeepSeek 开思考时不接受强制工具调用，44 轮里有 35 轮要追问一次；追问提示里「记录你的答复」被模型写进了答复，7 轮出现「已记录」「登记清楚了」这类没做过的事。这两条如果以后要在回复层开思考，得先修。
- 用户人工抽查（15 题，不标答法）还没做。

## 写文章可用的点

「快」和「想得深」不一定要二选一。不开思考只在计算题上真吃亏，其他题差别在评审波动之内。让回复层先答应、再把难题交出去细想，首字速度和质量可以兼得。另一个值得讲的是：盲评最容易犯的错，是评审看到的东西和用户看到的不一样。
