# 首句回复从 3 秒降到 1.6 秒，发出后立刻显示“正在读”

- 日期：2026-11-16
- 类型：优化 + 修复
- 相关提交：（见本篇所在提交）

## 问题

用户在公司电脑上试用时说：“我说话后，看不到信息是否被读了，并且第一句回答其实回的很慢。”账本里，一句话从发出到回复要 4～11 秒，可其中模型调用只占 0.4～2.5 秒。另外有一条消息卡了 90 秒才失败，失败时用户只看到一句笼统的“遇到问题”。

## 前后对比

本机分别起改前、改后两个全新服务，用独立的空测试库、真实 DeepSeek flash 接口，连发 6 条闲聊，从发出算到页面出现回复。

| 指标 | 改前 | 改后 |
|---|---|---|
| 服务刚启动后的第一句 | 19.5 秒 | 6.0 秒 |
| 之后 5 句的中位数 | 2.9 秒 | 1.6 秒 |
| 最快一句 | 2.6 秒 | 0.7 秒 |
| 发出后页面显示“正在读” | 没有 | 0.04 秒（网页实测 0.24 秒，含轮询） |
| 模型不回应时，多久得到答复 | 约 90 秒，只说“遇到问题” | 最多约 65 秒（三次各 20 秒，加上重试间隔），说明是模型服务没回应 |

改前用户发完消息，只看到自己的气泡，几秒钟内什么变化都没有。改后气泡下方马上出现“已送达”，被接手后变成蓝色的“正在读…”，回复到了这行字就消失。

分段耗时表和测量口径见 [docs/validation/first-reply-latency.md](../validation/first-reply-latency.md)。

## 怎么做的

- **根因一：每条消息现启动一个进程。** 执行循环跑在单独的 Node 进程里，每条消息都要新启动一个，再加载约 3000 个 JS 文件，本机要 1.2～2 秒，公司电脑（杀毒会逐个扫描）要 3～10 秒。改法：服务里始终预备好一个“已加载、还没接活”的进程，来一条消息就交给它，同时在后台再预备下一个。进程仍然一次一用，预备时不带任何任务数据，所以隔离方式完全没变。没有选“常驻一个进程反复用”，因为那样会改变现有的停止、清理和隔离方式，风险大得多。
- **根因二：第一次调模型时才导入 SDK。** 导入模型 SDK 要 5～11 秒，而且是在事件循环里同步做的，这段时间整个服务都卡着。改法：服务启动时在后台线程里先导入，并加载好证书库。异步客户端本身仍在事件循环里创建，因为它和所在的事件循环绑定（第一版整个放进线程里创建，每次调用都连接失败，量数时发现后改掉）。
- **90 秒挂起：调用没有自己的时限。** SDK 的超时只管每一次网络读，不管整次调用，接收层也只有整轮 90 秒的外层上限，所以一次卡住的调用会一直占到外层上限，重试机制根本没机会起作用。改法：每次模型调用都套上硬时限（对话接收 20 秒，执行层沿用原来配置的超时），超时算作临时故障，按原有的退避规则重试；最终失败时，告诉用户是模型服务没回应。这条规则对所有调用都生效，不针对哪一条消息。
- **轮询改唤醒：** 网页发来消息后直接唤醒调度器；只有命令行和定时任务这类从别处进来的工作还走轮询。
- **已读状态：** 由账本的事实推算（已存进库、已有运行接手、已出结果），合并在一起的几条消息共享同一个状态；一次查询就能算出来，测试断言 60 轮历史和 20 轮历史下的查询数相同。

## 没做到 / 边界

- 服务刚启动后的第一句仍要约 6 秒：主要是第一次建立到模型服务的 TLS 连接，以及服务端首个请求的冷启动。可以在启动时先发一个探测请求来预热，但那会多一次计费调用，所以这次没做。
- 前端仍然每 1.5 秒轮询一次，平均要多等 0.75 秒才看到回复。改成服务器推送是更大的改动，留到以后。
- 公司电脑上的实际改善还没测到，需要用户在那台机器上用一用。

## 写文章可用的点

“慢”的大头常常不在模型身上：先用账本时间戳把每一段拆开量，才发现 4～11 秒里模型只占 1～2 秒，剩下的是进程启动和包导入。另一个点是，“超时”只限制单次网络读时，并不能保证整次调用在多久之内结束。
