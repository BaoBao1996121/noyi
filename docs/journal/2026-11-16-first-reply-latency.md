# 首句回复从 3 秒降到 1.6 秒，发出后立刻显示“正在读”

- 日期：2026-11-16
- 类型：优化 + 修复
- 相关提交：（见本篇所在提交）

## 问题

用户在公司电脑上试用时说：“我说话后，看不到信息是否被读了，并且第一句回答其实回的很慢。”账本里，一句话从发出到回复要 4～11 秒，可其中模型调用只占 0.4～2.5 秒。另外有一条消息卡了 90 秒才失败，失败时用户只看到一句笼统的“遇到问题”。

## 前后对比

本机分别起改前、改后两个全新服务，用独立的空测试库、真实 DeepSeek flash 接口，连发 6 条闲聊，从发出算到页面出现回复。

| 指标 | 改前 | 改后 |
|---|---|---|
| 服务刚启动后的第一句 | 19.5 秒 | 6.0 秒 |
| 之后 5 句的中位数 | 2.9 秒 | 1.6 秒 |
| 最快一句 | 2.6 秒 | 0.7 秒 |
| 发出后页面显示“正在读” | 没有 | 0.04 秒（网页实测 0.24 秒，含轮询） |
| 模型不回应时，多久得到答复 | 约 90 秒，只说“遇到问题” | 最多约 65 秒（三次各 20 秒，加上重试间隔），说明是模型服务没回应 |

改前用户发完消息，只看到自己的气泡，几秒钟内什么变化都没有。改后气泡下方马上出现“已送达”，被接手后变成蓝色的“正在读…”，回复到了这行字就消失。

分段耗时表和测量口径见 [docs/validation/first-reply-latency.md](../validation/first-reply-latency.md)。

## 怎么做的

- **根因一：每条消息现启动一个进程。** 执行循环跑在单独的 Node 进程里，每条消息都要新启动一个，再加载约 3000 个 JS 文件，本机要 1.2～2 秒，公司电脑（杀毒会逐个扫描）要 3～10 秒。改法：服务里始终预备好一个“已加载、还没接活”的进程，来一条消息就交给它，同时在后台再预备下一个。进程仍然一次一用，预备时不带任何任务数据，所以隔离方式完全没变。没有选“常驻一个进程反复用”，因为那样会改变现有的停止、清理和隔离方式，风险大得多。
- **根因二：第一次调模型时才导入 SDK。** 导入模型 SDK 要 5～11 秒，而且是在事件循环里同步做的，这段时间整个服务都卡着。改法：服务启动时在后台线程里先导入，并加载好证书库。异步客户端本身仍在事件循环里创建，因为它和所在的事件循环绑定（第一版整个放进线程里创建，每次调用都连接失败，量数时发现后改掉）。
- **90 秒挂起：调用没有自己的时限。** SDK 的超时只管每一次网络读，不管整次调用，接收层也只有整轮 90 秒的外层上限，所以一次卡住的调用会一直占到外层上限，重试机制根本没机会起作用。改法：每次模型调用都套上硬时限（对话接收 20 秒，执行层沿用原来配置的超时），超时算作临时故障，按原有的退避规则重试；最终失败时，告诉用户是模型服务没回应。这条规则对所有调用都生效，不针对哪一条消息。
- **轮询改唤醒：** 网页发来消息后直接唤醒调度器；只有命令行和定时任务这类从别处进来的工作还走轮询。
- **已读状态：** 由账本的事实推算（已存进库、已有运行接手、已出结果），合并在一起的几条消息共享同一个状态；一次查询就能算出来，测试断言 60 轮历史和 20 轮历史下的查询数相同。

## 没做到 / 边界

- 服务刚启动后的第一句仍要约 6 秒：主要是第一次建立到模型服务的 TLS 连接，以及服务端首个请求的冷启动。可以在启动时先发一个探测请求来预热，但那会多一次计费调用，所以这次没做。
- 前端仍然每 1.5 秒轮询一次，平均要多等 0.75 秒才看到回复。改成服务器推送是更大的改动，留到以后。
- 公司电脑上的实际改善还没测到，需要用户在那台机器上用一用。

## 写文章可用的点

“慢”的大头常常不在模型身上：先用账本时间戳把每一段拆开量，才发现 4～11 秒里模型只占 1～2 秒，剩下的是进程启动和包导入。另一个点是，“超时”只限制单次网络读时，并不能保证整次调用在多久之内结束。

## 第二步：首句“最快速度、不失质量”（同日追加）

用户要求：“我们的第一句话一定要快，最快速度，但是又不失质量的先回复。然后可以慢慢做事。”

现状核对：接收层本来就是“先回一句、再交后台”。闲聊直接回答；要干活的，首句是模型自己写的回执（复述要做什么），然后转后台执行。所以这一步不需要改变产品行为，目标是把首句前的等待压到只剩模型本身。

目标值：服务预热完成后，首句中位数 ≤ 1.5 秒、慢的 ≤ 2.5 秒；“正在读”≤ 0.3 秒。

又做了两件事：
- **启动时先连上模型服务。** 一个进程里第一次连接要 4.6 秒（域名解析、TLS、代理探测），之后每次只要 0.1 秒。现在服务一启动就用“列出模型”接口先连一次。这个接口不计费、不带任何用户数据，也不记成一次模型请求。
- **页面改为“有变化立刻返回”。** 页面原来每 1.5 秒问一次，回复平均要多等 0.75 秒才能看到。现在页面带上自己看到的版本号来问，服务端在账本有任何写入时立刻返回，最多挂 20 秒；判断有没有变化只读一个计数器，不查库。

| 指标（本机，真实 DeepSeek） | 第一步后 | 第二步后 |
|---|---|---|
| 启动后第一句（等 8 秒再发） | 6.0 秒 | 1.7 秒 |
| 之后中位数（服务端口径） | 1.6 秒 | 1.4 秒 |
| 网页里从点发送到看到回复 | 约 2.2 秒 | 1.0～2.8 秒，中位约 1.9 秒，和模型这次答得快慢一致 |
| 网页里看到“正在读” | 0.24 秒 | 0.21～0.25 秒 |

拆开看，现在首句前的各段（入库、接手、预备进程、拼上下文）合计 0.03～0.3 秒，其余全是模型本身的 0.8～2 秒。上下文前缀已经能命中模型服务的缓存（5700 个输入 token 里命中 2800～5500），命中多少对耗时影响不明显。

再往下提速只剩改变产品行为的做法，已经交给总控决定：比如回复边生成边显示（流式），或者先给一句固定回执、再补完整回复（这会变成空洞的“收到”，和用户要求的“不失质量”冲突，不推荐）。

刚启动就马上发的第一句仍要几秒：要等后台导入 SDK、建立连接，这些在服务启动后约 5～8 秒内完成。

## 第三步：回复边生成边出字（同日追加）

用户在决策卡片上选了方案 A：回复边生成边显示。要求首字约 0.5 秒，质量不变，承诺账本的规则一条不松。

怎么做的：
- **接收协议不变，只是改成流式接收。** 模型仍然一次调用“记录决定”的工具给出整句。区别是现在边收边拼工具参数，参数里回复正文那一段（闲聊的回答，或接活时的回执）一出现，就把已经到达的部分解出来当作“草稿”显示。转义字符、半个 \u 编码、表情的代理对都等完整了再显示，不会出乱码。
- **草稿只存在内存里，不进账本。** 草稿没有送达编号，不能被标成已读，不算送达，也不能当兑现依据。整句收完后照旧走原来的核对：回复里的承诺要拦下或登记，结论引用要逐字比对。核对通过才写成正式回复，草稿随即被正式回复替换。
- **核对没通过时，用户看得出来。** 被拦下的那版会被撤回。如果最后送达的回复和之前显示的不一致（例如模型先写了一句没登记的承诺，被拦下后重写），页面在原位置留一行“刚才显示的回复已更正为下面这条”；彻底失败时显示“刚才显示的回复没有通过核对，已撤回”。提示保留 30 秒。
- 页面原本就是“有变化立刻返回”，草稿每变一次版本号加一，页面立刻拿到。判断变化仍只看计数器，不查库。

| 指标（本机，真实 DeepSeek，6 条） | 第二步后 | 第三步后 |
|---|---|---|
| 首字（服务端口径，中位 / 最快 / 最慢） | 等于整句：1.4 秒 | 0.86 / 0.59 / 1.35 秒 |
| 整句送达（服务端口径，中位） | 1.4 秒 | 1.5 秒，没有变慢 |
| 网页里首字（3 条较长的问题） | 等于整句：1.0～2.8 秒 | 1.2～2.4 秒，整句在 2.7～6.3 秒 |

没做到的部分：首字目标 0.5 秒只在最快的一条达到，中位 0.86 秒。剩下的时间是模型服务吐出第一个参数片段本身要的 0.5～1 秒（单独测流式接口也是这个数），程序这边首字前的开销仍是 0.03～0.3 秒。长回复的好处最明显：一条 6.3 秒才写完的回复，1.6 秒就开始出字。

测试：新增流式拼装、草稿解析（转义、半截编码、表情）、草稿替换 / 更正 / 撤回、草稿存在期间账本里没有任何送达记录、页面长轮询随草稿立刻返回。
