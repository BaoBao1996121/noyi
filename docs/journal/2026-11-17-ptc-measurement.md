# 要不要让模型写代码批量调工具：先量账本，再做个小原型

- 日期：2026-11-17
- 类型：阶段收口（测量与原型，未改产品行为）
- 相关提交：（见本篇所在提交）

## 问题

Anthropic 有一种叫 PTC（programmatic tool calling）的做法：模型写一段代码，在代码里并行调用搜索、读网页这类只读工具，在代码里先把结果过滤掉，只把结论交回模型。宣传的好处是模型往返少了，上下文也不会被网页正文撑大。Noyi 用的是 DeepSeek，要用就得自己搭。动手之前，先用账本里的真实任务算一算它能省多少。

## 前后对比

这次没有改产品。下面是现状测量和原型对比，完整口径见 [docs/validation/ptc-measurement.md](../validation/ptc-measurement.md)。

现状（18 件工具调用不少于 5 次的任务，174 轮，314 次工具调用）：

| 指标 | 数值 |
|---|---|
| 耗时：模型 / 工具 / 其他 | 47% / 52% / 2% |
| 一轮已经发多个调用的轮次 | 45%，但执行是串行的 |
| 输入 : 输出 token | 32 : 1 |
| 工具结果里网页正文的占比 | 86% |
| 上下文增长里工具结果的占比 | 至少 61% |
| 机械往返（只是逐个打开上一步给的链接或翻页） | 28% 的轮次 |

PTC 上限估算：保守档省 28% 的轮数、29% 的输入 token、12% 的总耗时；乐观档分别省 61%、69%、约 42%（其中 12% 来自工具并行）。

原型（3 道真实风格的多步题，DeepSeek flash 开思考）：

| 指标 | 逐步调用 | PTC 原型 |
|---|---|---|
| 模型轮数 | 3～14 | 2～3 |
| 输入 token | 1.4 万～34 万 | 1200～3500 |
| 输出 token | 1200～5300 | 1400～11000 |
| 代码一次跑通 | — | 6 次里 5 次 |
| 答案里的来源链接 | 7～11 个 | 2～11 个 |

## 怎么做的

- 用只读方式连接账本，一件任务一件任务地算：模型请求的起止时间、每次工具调用的起止时间、每轮的输入输出 token、每次工具结果的字符数。旧账本没记工具结束时间，就用两次模型请求之间的空档来估。
- 「机械往返」用一条通用规则判定：一轮只发只读调用，而且要读的每个 URL 都已经出现在之前的工具结果里。不靠人工挑样例。
- 原型直接复用产品里的搜索和读页实现，只把「模型怎么调用工具」换成「模型写一段异步 Python」，两种做法拿到的数据源完全一样。
- 顺带查到：Pi Agent 本身支持一轮里的多个工具并行执行，Noyi 的桥接层把它设成了串行。

结论：完整 PTC 先不做。先把只读工具改成同一轮并行执行，零 token 代价，省约 12% 的时间。再做一个「批量读页并只返回相关片段」的工具，拿到大部分 token 收益，也不用代码沙箱。

## 没做到 / 边界

- 原型的答案没做质量盲评，只数了来源链接。PTC 的答案更短、引用更少，因为代码里的过滤规则是事先猜的。
- 原型每题只跑 2 次，样本小，只能看方向。
- 原型的头三批运行全部失败，原因都在我写的沙箱上（没放开 import、接不住 `asyncio.run` 写法、提示词被误改），不在模型。自建 PTC 真正的工作量在执行环境。

## 写文章可用的点

模型已经会一轮发好几个工具调用，但它们是一个接一个执行的。很多「让 Agent 更快」的花哨方案里，最大的一块收益其实是把一个串行开关改成并行。PTC 省掉的主要是输入 token，代价是更多的输出 token。在一轮就能问完的中等题上，这笔账不一定划算。
