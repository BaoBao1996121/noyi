# 重启先等旧进程放开数据目录，再启动新的

- 日期：2026-11-16
- 类型：修复
- 相关提交：（本篇所在提交）

## 问题

在本机执行 `noyi restart`，有一次结果是“启动未完成”，服务停在那儿。原因是两个步骤之间有空隙。停止脚本只看页面还应不应答，页面一不应答就算“已停止”。可那时旧进程还在收尾，比如保存执行状态、结束模型连接、关掉 Pi 子进程，数据目录的锁还在它手里。新进程这时启动，一拿锁就失败退出。

家里电脑走的是同一条路：崩溃后自动重启、升级时切换版本。那边没人看着，失败一次就停在那里。守护进程还会把这种“刚启动就退出”记成一次崩溃，连着几次就会误判成崩溃循环，不再重启。

## 前后对比

本机实测一次停止：页面 2.2 秒就不应答了，锁要到 5.0 秒才放开，中间有 2.8 秒的空隙。

| 场景 | 改前 | 改后 |
|---|---|---|
| `noyi restart` | 落进这 2.8 秒就启动失败 | 停止要等锁放开才返回，然后再启动；本机实测 32 秒内完成，服务正常 |
| 刚停又马上点“启动” | 同样会失败 | 提示“上一次的服务还在退出，等待它释放数据目录…”，放开后再启动 |
| 家里守护进程崩溃后重启 | 被锁挡住时立刻退出，记成一次崩溃 | 状态写成“等锁”，不记崩溃，锁放开后再启动 |
| 升级切换版本 | 只看页面和守护状态，备份可能和收尾的旧进程同时进行 | “已停止”还要求数据目录已经放开 |

## 怎么做的

- 根因是把“页面不应答”当成了“进程已经退出”。修法是统一用服务自己拿的那把系统锁来判断“已停止”：试着拿一下，拿得到就说明没有进程占着，拿不到就说明还有进程在收尾。进程死掉时系统会自动放锁，所以不会被残留文件误挡，也不需要按进程号去猜。
- 这个判断放在家里工具共用的模块里，只用标准库。桌面的启动 / 停止 / 重启、家里的守护进程和升级器都调同一个函数，不各写一份。
- 停止时，页面不应答以后再等锁放开，最多 60 秒。超时就明确说“旧进程 60 秒后仍未退出、还占着数据目录”，并告诉用户去结束残留进程，不会假装成功。启动前也检查一次，这样别的入口刚停完就启动，也会先等。
- 守护进程碰到锁被占时不启动，把状态记成“等锁”和开始等的时间，等锁放开再起，不消耗崩溃次数。

## 没做到 / 边界

- 守护进程在“等锁”状态下不会自己去结束占锁的进程。占锁的可能是用户手动启动的另一份服务，强行结束可能丢掉它正在保存的状态。所以只把状态写清楚，留给人判断。
- 测试：停止要等锁放开才返回；锁一直不放时超时报错，提示写清原因；启动会先等正在退出的旧服务；守护进程在锁被占期间不记崩溃，锁放开后照常启动。

## 写文章可用的点

“它不应答了”和“它已经退出了”是两件事。判断能不能接手，要看接手时真正会撞上的那把锁，而不是看一个间接信号。
