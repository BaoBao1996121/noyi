# codemode 接进产品两轮验收都没过：按工具分简单题贵 42%，两种都能调难题质量下降，暂不上线

- 日期：2026-11-18
- 类型：功能（验收未过，代码留在分支 feat/codemode，未合 main）
- 相关提交：857f51e、0356a5d（分支 feat/codemode，未合 main）；上一篇实验见 [2026-11-18-codemode-experiment.md](2026-11-18-codemode-experiment.md)

## 问题

实验显示，让模型写一段程序批量读网页（codemode），多来源调研题的输入 token 能省约 40%。用户决定立项接进产品，并拍板"按工具分吧"：返回大段正文的读取工具只能在程序里调，搜索只能直接调，用来压住搜索次数。上线前按预先写好的四条门槛验收：交付 ≥14/15；盲评 ≥ A 组 − 0.5；输入 token 合计 ≤ A 组；简单题 Q1 的 token ≤ A 组 × 1.1。

## 前后对比

## 怎么做的

- 每个工具在定义里声明调用方（`ToolSpec.callers`：direct / code，不填默认 direct）。限制放在所有调用的统一入口 `execute_tool` 里，按"这次调用来自模型还是程序"判断，不在 bridge 里按工具名写分支；只有可并发的纯读取能声明给程序调。
- 程序里每次工具调用都走同一个入口，照样过权限、记账、引文核对，账本里记着它属于哪次程序调用。
- 同一任务里命中已存快照的重复读不扣工具额度，对直接调和程序调一视同仁；兜底靠两条：重复读不算新进展（停滞计数照常累加），一个程序最多 40 次调用、60 秒。
- 停滞计数里一个程序算一次活动，里面有一次新进展就算进展。
- 程序读到的图片照样附给模型看，识图不受影响。

## 没做到 / 边界

- **简单题变贵的原因**：Q1 多花的不是读页，是模型轮数。逐步调用时模型读一次页就看到全文；在程序里，模型倾向先返回每页前 3000～6000 字"看一眼"，发现关键段落不在前面，再写第二、三个程序按关键词去找，最多一次写了 4 个程序。每多一轮，整段上下文要重新送一次，所以 token 涨了 42%、耗时多 9 秒。5 次里有 2 次一个程序就收尾，这两次和 A 组持平。
- fetch_page 命中缓存时直接返回全文的评估：读页按 8000 字一页，程序可以循环读完再在程序里筛，拿全文不是问题；问题在模型没有一次就把要找的东西写进程序。要让简单题回到 A 组水平，可选方向有：给读页加"按关键词取段落"的参数，或允许简单题照旧直接读页。这是产品取舍，留给下一步决定。
- Q0 的盲评低了 1.4 分（16.3 对 17.7），总分靠 Q1、Q2 拉平，余量只有 0.03 分，质量门槛是勉强过的。
- 约 39 个旧测试按"直接调读页"的写法，改成按工具分后会失败；验收没过，这次没改。

## 写文章可用的点

省 token 的手段换到简单任务上可能反而变贵：程序化调用省的是"中间结果不进上下文"，但如果模型要多写几次程序才找准位置，多出来的轮数比省下的还多。预先写死"简单题不许变贵"这条门槛，才看得出来。

## 第二轮：读工具两种都能调（同日重跑，也没过）

用户拍板"重跑验收"，按 Pi 默认的 `on` 模式改：fetch_page、read_source、read_artifact、web_search 都可以直接调，也可以在程序里调；写入、流程类仍只能直接调。工具描述恢复成只说自己做什么；codemode 引导改成通用说法："一两次读取就能答时直接调；要多次查找、读多页、做过滤汇总时用 codemode"。门槛开跑前写定：交付 ≥14/15；盲评 ≥ A − 0.5；Q1 token ≤ A × 1.05；Q0 + Q2 token 比 A 至少省 20%。口径与上一轮相同，A 组复用。

| 题 | 交付 | 盲评 A / 新 | 输入 token A / 新 | 平均耗时 A / 新 | 模型轮数 A / 新 | 每任务搜索 A / 新 | 选用 codemode |
|---|---|---|---|---|---|---|---|
| Q0 多来源对照 | 5 / **2** | 17.9 / **9.9** | 195 万 / 258 万 | 129s / 159s | 16.2 / 21.2 | 2.8 / 4.2 | 5/5 |
| Q1 查一个发布日期 | 5 / 5 | 19.7 / 19.0 | 26.9 万 / 37.6 万 | 19.4s / 31.7s | 4.4 / 5.4 | 1 / 1 | 2/5 |
| Q2 查官方文档 | 5 / 5 | 18.8 / 17.5 | 51.6 万 / 79.4 万 | 45s / 79s | 6.4 / 9.2 | 0.8 / 0.2 | 5/5 |

四条门槛全没过：交付 12/15；盲评 15.47 对 18.8；Q1 token 是 A 的 1.40 倍；Q0 + Q2 是 A 的 1.37 倍（不但没省，反而多）。这一轮的 A 组分数和上一轮不同（18.8 对 18.17），推断是盲评按批评分，同一份报告和不同对手放在一起时分数会浮动。

看到的现象：

- **Q0 三次没交付，都是用完 24 次模型调用**。这三次模型在直接读页和程序之间来回换，写了 13～23 个程序，多数程序只读一两页，没有用到"一个程序并行读多页"的好处。搜索也从 2.8 次涨到 4.2 次，搜索放进程序以后没有压住。
- **Q1 选用 codemode 的比例是 2/5**，引导在简单题上部分起了作用。但没用 codemode 的 3 次，每轮输入 token 也比 A 组多约 1,300～1,400（约 14,000 对 11,800），推断主要是 codemode 工具说明和引导本身占的位置：只要工具挂着，每轮都要付这笔钱。所以就算模型每次都选对，Q1 也很难压到 A 的 1.05 倍以内。
- 两轮合起来看：把读页限制在程序里（第一轮），简单题多 42%；两种都放开（第二轮），模型在难题上来回切换，难题也变贵、质量明显下降。这个模型（deepseek-flash）在 Noyi 的任务循环里，目前都没有把 codemode 用出实验时那 40% 的节省。实验时的 C 组是专门的"只给 codemode"设置，和产品里还挂着十几个其他工具的环境不同。

## 第二轮之后的判断

- 不上线。代码留在分支 feat/codemode（857f51e 第一轮、0356a5d 第二轮），未推送，main 和家里那台都没动，无需回退。
- 若还想继续，比较像样的方向是知识文档里提到的 DeepSeek Harness 做法：不让模型每轮都在两条路之间选，而是按任务配置决定这一类任务挂不挂 codemode（例如只给多来源调研类任务挂），并且挂上后读页只走程序。这需要先有可靠的"这是调研类任务"判断，现在回复层的难度判断准确率只有 15/22，所以暂时搁置。
