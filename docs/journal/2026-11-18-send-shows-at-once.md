# 点「发送」后消息立刻出现：从 0.76 秒降到 0.06 秒，与网速无关

- 日期：2026-11-18
- 类型：优化
- 相关提交：（见本篇所在提交）

## 问题

上一篇（`2026-11-18-mobile-load.md`）把手机在外面打开页面的时间压了下来，但没动发送。用户反馈：在家点「发送」只是稍卡，在外面用手机点「发送」要卡很久才发出去。

原因在页面的发送流程：点发送后先等 `POST /api/messages` 回来，回来后才清空输入框，再等一次完整的 `GET /api/state`（压缩后约 22 KB）回来，消息才出现在对话里。这两步是串行的，在这期间输入框里的字还在，发送按钮是灰的，对话里什么都没有。局域网里往返不到 1 毫秒，感觉不到；外网每次往返几百毫秒，经 Tailscale 中转（DERP）时更久，就变成了「卡很久」。

## 前后对比

测量口径：新增的 `scripts/measure-send.py`。造一个约为真实库 3 倍的临时库（24 件事、63 条消息、87 条回复，全是造的数据），起一个后台服务关闭的 Noyi，前面加上一篇的节流代理（每个请求加固定往返，所有请求共用一条限速链路）。Chromium 手机视口打开页面，等空闲后输入一条消息点发送，在页面里计时到「这条消息出现在对话里」和「输入框清空」。每种条件连发 3 条取中位数。

| 指标（往返 300 毫秒、2 Mbps） | 改前 | 改后 |
|---|---|---|
| 点发送 → 消息出现在对话里 | 0.76 秒 | 0.06 秒 |
| 点发送 → 输入框清空 | 0.40 秒 | 0.06 秒 |
| 消息出现前要等的请求 | 2 个，串行（发送 + 整页状态） | 0 个 |
| 发送后多下载的整页状态 | 1 次（约 22 KB） | 0 次 |

| 指标（往返 800 毫秒、1 Mbps，模拟中转） | 改前 | 改后 |
|---|---|---|
| 点发送 → 消息出现在对话里 | 1.11 秒 | 0.11 秒 |
| 点发送 → 输入框清空 | 0.94 秒 | 0.11 秒 |

改后的时间只是页面重画一次的时间，和网络无关：往返从 300 毫秒加到 800 毫秒，改前多了 0.35 秒，改后基本不变。

服务端本身不慢：直连（不经代理）时 `POST /api/messages` 中位数 3.4 毫秒，`GET /api/state` 约 11 毫秒。慢的全是网络往返，所以服务端没改处理逻辑。

## 怎么做的

根因属于一类问题：**界面上的结果要等网络确认后才显示**。往返越贵越慢。修法是把「显示」和「确认」拆开，所有从输入框发出的消息都走同一套，不针对某个页面：

- **新增发件箱 `web/outbox.js`。** 点发送时消息进入发件箱，对话立刻画出它，标「发送中…」，输入框和附件立刻清空；请求在后面排队发出（一次一条，保证顺序）。回执回来标「已送达」；之后长轮询带回的状态里出现这条消息，就由账本里的正式消息接替显示，发件箱删掉它。
- **按 nonce 认领，而不是按消息号。** 状态接口给网页发出的消息加了 `nonce` 字段（只对 `source='web'` 的消息，其他来源为空）。这样哪怕状态比回执先回来，或者回执在路上丢了，页面也能认出「这就是我发的那条」，不会画两遍。
- **失败保留原文和原 nonce。** 请求没到服务器（断网、超时），气泡下面标「没发出去 · 点一下重试 · 改一改」。重试用同一个 nonce 和完全相同的内容，服务端本来就按 nonce 去重（同 nonce 同内容返回原回执），所以连点、或者其实上次已经到了，都只会有一条。服务器明确拒绝的（比如资料不属于当前会话），显示原因；「改一改」把原文、附件、回复引用、指定成员放回输入框，内容没改时沿用原 nonce。
- **发件箱存在本机。** 按资料库分开存进 localStorage。发送途中关掉或刷新页面，重新打开时把没确认的那条用原 nonce 再发一次；没发出去的仍然显示在对话里，可以重试。
- **发送后不再整页刷新。** 发送改变了账本，页面本来挂着的长轮询（`/api/state?since=`）会立刻带着新状态回来，再拉一次全量只是重复下载同样的 22 KB。所以去掉了发送后的 `refresh(true)`。离线或页面在后台时，轮询本来就每 1.5 秒或 5 秒问一次。
- 「已记入群聊，没有启动新任务」照旧在回执回来时提示。桌面页和手机页共用 `app.js`，行为一致。发送时不再禁用发送按钮，也不再禁止切换会话，因为发件箱里的消息自带房间号。

比较过的方案：

- 只把「清空输入框」提前到请求前：输入框清空了，但对话里仍然什么都没有，用户会以为消息丢了。
- 用回执里的数据拼一条正式消息塞进 `state.data.messages`：要在前端复制服务端的展示字段（时间、接手成员、意图状态），两边容易不一致。发件箱只管「还没回来的」，回来后完全以账本为准。
- 发送后改成增量刷新：长轮询已经是「有变化立刻回来」，不用另做增量接口。

测试 `tests/test_send_outbox.py`：用 node 跑发件箱，配一个按 nonce 去重的假服务端，覆盖这几种情况：发送中立刻可见并转成正式消息；断网失败后连点两次重试加一次原样重发，服务端只收到一条；被拒绝时显示原因并能取回输入框；多条按顺序发出；刷新页面后续发被打断的那条，不重复；当前视图不显示的消息不会一直挂着。另有一条接口测试检查状态里带回 nonce，一条检查发送流程里不再整页刷新。

真实浏览器里点过一遍（Chromium 手机视口，临时库）：正常发送、断网发送后恢复网络点重试、带图片附件发送、断网发送后刷新页面。四种情况消息都立刻出现，库里每条消息只有一份，图片作为任务资料记进了这条消息。

## 没做到 / 边界

- 手机上的真实表现还没测，数字来自本机模拟。
- 回复本身的速度（模型多久开始回）不在这次范围内，那取决于模型和网络，页面只能让「发出去」这一步不再等。
- 发件箱存在浏览器本地。换一台设备打开，看不到另一台上没发出去的消息。

## 写文章可用的点

弱网下「按钮一按就有反应」比把请求做快更重要。把显示和确认拆开，再用一个客户端生成的 nonce 把两边对上，乐观更新就不会因为重试而重复，也不会因为回执丢失而画两遍。
