# 体验对齐方案（2026-11-05 用户确认）

状态：方案已定，未实现。验收标准是第 6 节的对照测试，不是单元测试通过。

## 1. 依据

- 用户本机 Grok Bot 的真实聊天记录（7 个 Bot，约 800 条），结构统计加人工阅读，原文私有不进仓库。
- 2026-11-05 在新建的实验 Bot 上自动跑了两轮体验测试（15 项），只记录行为，不推断 Grok 的内部机制。
- 结论：Grok 好用不在于功能多，在于几条很稳的规矩：先秒回一句，做完立刻推送，中间保持安静，只在有变化时打扰，被质疑时先核实。这些规矩在我们的代码里还没有落地，补上是本方案的重点。

## 2. 决定

| ID | 决定 | 原因 |
|---|---|---|
| X-1 | 先做网页，第二个渠道是飞书，开源后再考虑 App 等展示形态。何时说、说什么由核心决定，渠道只负责显示 | 换渠道时不用重写体验规矩 |
| X-2 | 第一批能力依次是：网页搜索与读取、交付页面、MCP 接入。执行本机命令延后 | Grok 的交付靠这三类能力；执行命令风险最高 |
| X-3 | 搜索和读网页做成我们自己的插件。搜索后端可以替换，第一版用百炼 Responses 接口的 web_search，读网页由我们自己抓取和清洗 | 每次调用都进账本、来源可核实。百炼兼容模式的联网开关不返回来源，不采用 |
| X-4 | 搜索预算：单个任务 30 次，每天 200 次，超过就停下来问用户，数值写在配置里 | 搜索按次计费，不能悄悄花钱 |
| X-5 | 回执和交付的措辞由模型写，代码把关。回执不超过 60 字、复述具体要做的事、不得出现承诺完成的说法；写坏或超时时退回模板 | 现在的回执是固定套话，不像同事说话 |
| X-6 | 「已开跑」这句只在任务真正开始执行时发；交付固定为一句结论、最多三条要点、链接 | 说的是真实状态；与 Grok 的三段节奏对齐 |
| X-7 | 用户明说「记住」「以后都这样」时直接生效，并回一句复述确认。模型自己推断出的偏好只作为提议，用户确认后才生效。记忆都能查看、修改和删除 | 用户不想同一件事说两遍，也要防止模型乱记 |
| X-8 | 模型手里只保留这些工具：任务、停止与继续、提问、定时与盯梢、记忆、一层子任务。进度和证据由系统从账本自动生成。目标复盘和策略提案、审批这一套对模型隐藏，代码暂时不删 | 工具从 29 个降到约 12 个，规则大幅缩短，模型把精力花在干活上 |
| X-9 | 长任务不定时汇报进度。第一次超过 20 分钟时，发一句带实际数字的进度，数字从账本统计。一有结果立刻推送。卡住时用一句话说清卡在哪、要用户做什么 | 真实记录里出现过用户 24 分钟、47 分钟后来催问的情况 |

## 3. 不做

- 不自己做手机 App（开源前）。
- 不按固定间隔发「还在做」这类进度。
- 不在模型可见的工具里保留目标复盘和策略审批；需要回顾时，作为普通任务读账本、写报告。

## 4. 实施顺序

每一步单独提交，可以单独回退。

1. **瘦身（X-8）**：隐藏管理工具，进度由账本生成，压缩系统规则。这一步改变了模型收到的内容，必须用真实模型（qwen3.7-plus）跑一遍现有场景，确认没有退化。（已完成，见下方「进展」）
2. **说话规矩（X-5、X-6、X-7、X-9）**。（已完成，见下方「进展」）
3. **装能力（X-2、X-3、X-4）**：搜索和读网页插件，带预算；交付页面。（已完成，见下方「进展」）
4. **对照验收（第 6 节）**。MCP 接入放在验收之后。

### 进展

- 第 1 步（2026-11-05）：普通任务可见工具 24 → 19，系统提示约 10.2K → 7.9K 字符（prompt_version 11）；回顾改为普通报告任务；目标进度由账本写 `ledger_progress`。离线全量 335 通过，1 项为改动前已有的失败（`test_timeout_during_pending_read_finalizes_operation_as_interrupted`）。真实 qwen3.7-plus 跑 M5 工作坊场景两格：solo 6 次调用 33 秒、parallel（2 个 Worker）27 次调用 87 秒，均成功，rubric 10 项都覆盖，缺失的可选资料都如实披露，没有调用隐藏工具。回顾任务只有离线测试（真实 Pi 加脚本模型），未用真实模型跑。
- 第 2 步（2026-11-05）：规则集中在 `speech.py`。
  - 回执由模型写，代码检查：超过 60 字或出现「已完成 / 写好了 / 见附件」这类说法，就退回模板。
  - 「已开跑」在任务第一次真正开始执行时由代码发一次；用户说继续时发「已重新开跑」。只安排不交付的任务、子任务、定时任务和回顾不发这句。
  - 交付消息只留第一句结论加最多三条要点，其余放在附件里。
  - 用户说「记住 / 以后都这样」时直接存成记忆并复述；没有明说的不存。
  - 任务第一次超过 20 分钟时，发一句带账本数字的进度。
  - 卡住时用一句话说清卡在哪、要用户做什么。
  - 验证：离线全量 352 通过，另有 1 项为原有失败。真实 qwen3.7-plus 跑了 5 句话：回执都复述了具体要做的事，「记住」立即生效，「这次先写结论」没有被存成长期偏好，闲聊直接回复。20 分钟进度和「已开跑」只有离线测试，还没在真实长任务里观察过。
- 第 2 步补测（2026-11-06）：真实长任务（2 个 Worker，进度阈值临时调到 30 秒）回执 17 秒、进度句带账本数字、82 秒交付三条要点。据此修了三处：进度不再显示「0 分钟」；交付是一整段时按句拆成结论加要点；回执后 10 秒内开工就不再补「已开跑」（这一条只有离线测试）。
- 模型换到本机 new api 网关（2026-11-06）：回复用户用 Opus 5.5 low，干活用 Opus 5.5 medium；搜索仍用百炼单独的密钥。Magpie 路由记录确认档位原样转给 new api（new api 之后是否保留无法从本机看到）。真实跑了 5 句对话（每句 4–10 秒，结果与千问一致）和一个联网任务（1 次搜索、2 次读网页，62 秒交付、验收通过）。
- 第 3 步（2026-11-06）：联网插件 `web_search` / `fetch_page`，每任务 30 次、每天 200 次搜索预算，超了让模型交付并说明哪些没核实，或问用户；交付里引用的网页必须真读过；通过验收的成果有独立交付页 `/r/{task_id}`。真实 qwen3.7-plus 查「Python 3.14 最新补丁版本」：1 次搜索、3 次读网页，84 秒交付，引用都能点开到原网页。

## 5. 待核实

- 百炼 web_search 的单价仍未核实。已实测：qwen3.7-plus 可用，来源在 `web_search_call.action.sources[].url`（一次约 30 条），一次搜索约 16 秒，账单次数在 `tool_usage.web_search.num_requests`。
- Grok 在忙时插话会显示「发送失败」（19 次中出现 3 次），原因未定。我们的设计是让插话排队，需要在第 4 步验证。

## 6. 完成标准

把两轮对 Grok 的测试原样在我们的网页上再跑一遍，逐项对照：

| # | 场景 | Grok 的表现（标准） |
|---|---|---|
| 1 | 闲聊 | 一句话答完，不会接着自己干活 |
| 2 | 长任务 | 秒回 → 「已开跑，做完怎么给你」→ 一有结果就推送；中间不发进度 |
| 3 | 运行中插话 | 立即回答，后台任务不受影响 |
| 4 | 运行中改需求 | 一句确认，再说明「改原成果」，改完给同一个链接 |
| 5 | 停下再继续 | 一句「已停」；说继续后一句确认，再说明已重新开跑 |
| 6 | 做不到的事 | 如实说做不到，不编结果，告诉用户要补什么 |
| 7 | 先问再做 | 用选项卡提问，不催；只答了一部分就只追问剩下的 |
| 8 | 定时提醒与删除 | 一行事件 + 具体时间；到点触发；一句话删干净 |
| 9 | 记住偏好 | 下一次交付就照做 |
| 10 | 碎句连发 | 合并成一次回答，不重复回答 |
| 11 | 「这个你别管了」 | 只停当前话题，后台任务不受影响 |
| 12 | 有变化才说 | 没有变化就零消息 |
| 13 | 用错误说法纠正它 | 不盲从，指出对方说错了 |
| 14 | 追问数据核实 | 先核实再答，承认过时，给出新数据 |
| 15 | 超过 20 分钟的任务 | 只发一句有实际数字的进度（X-9，这是我们比 Grok 多做的） |

15 项都做到才算完成。做不到的项要写明原因和补救计划，不能算通过。
