# PTC（模型写代码批量调用只读工具）值不值得做：账本测量与最小原型（2026-11-17）

口径：只读测量，不改产品代码。统计脚本、原型脚本、原始结果都放在本机不进 Git 的临时目录；本文只放统计数字和脱敏后的任务类型。

PTC 指 Anthropic 的 programmatic tool calling：模型写一段代码，在代码里批量、并行地调用工具，在代码里先过滤结果，只把结论交回模型。官方说明见 <https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling>。我们用 DeepSeek，没有现成的，要做就得自己搭。

## 样本

账本里工具调用不少于 5 次的任务一共 18 件：自用库 5 件，加上 DeepSeek flash 的 3 套验收库共 13 件。模型都是 DeepSeek flash 官方接口，执行层都是 Pi Agent。自用库只有 10 件任务，单看它不够 8 件，所以把验收库也算进来。验收库的题目同样是真实风格的多步调研。

| 类型（脱敏） | 件数 | 工具调用次数 |
|---|---|---|
| 生活类资料调研（多来源对比、写报告） | 5 | 5～31 |
| 技术 / 产品事实调研（读官方文档、对比版本） | 9 | 6～46 |
| 读本地资料后写文档 | 2 | 6～7 |
| 关注 / 跟进类操作（非调研） | 2 | 6 |

合计 174 轮模型往返，314 次工具调用。

## 1. 现状测量

### 耗时拆成三块

| | 合计秒数 | 占比 |
|---|---|---|
| 模型请求 | 874 | 47% |
| 工具本身 | 966 | 52% |
| 其他（调度、等待） | 35 | 2% |
| 总计 | 1874 | |

- 模型每轮平均 5.0 秒。
- 自用库的操作表记了每次工具的结束时间，工具耗时是实测。旧验收库没记结束时间，工具耗时用「相邻两次模型请求之间的空档」估算，里面含少量调度时间。所以「其他」只有 2%，调度不是瓶颈。
- 工具耗时几乎全是读网页：单页 0.7～29 秒不等，命中本地缓存时 0.02 秒。

### 往返轮数、每轮几个工具

- 平均每轮 1.80 个工具调用。45% 的轮次（174 轮里的 79 轮）已经一轮发了多个调用：2 个的 44 轮，3 个的 14 轮，4 个的 18 轮，5～6 个的 3 轮。**模型已经会一轮并发多个调用。**
- 一轮里的多个调用目前是**串行执行**的：桥接层把每个工具都设成 `executionMode: 'sequential'`，Pi 的 `toolExecution` 也是 `'sequential'`。Pi 本身支持并行执行（`executeToolCallsParallel`），只是没开。
- 自用库 5 件任务里，同一轮的多个工具如果并行执行，工具总耗时能从 208 秒降到 156 秒（省 52 秒，按「每轮只等最慢的一个」计算），约占这 5 件任务总耗时的 12%。

### 上下文 token 里工具结果占多少

账本的每次模型请求都记了输入、输出 token，以下是实数。只有「字符换 token」这一步是估算。

- 输入与输出之比是 32 : 1（输入 406.6 万 token，输出 12.6 万 token）。花费和耗时主要由反复带上的上下文决定。
- 工具结果合计 143 万字符，其中**网页正文占 86%**，搜索结果占 12%。
- 每件任务从第一轮到最后一轮，输入 token 共增长 32.3 万；同期模型自己的输出只有 12.6 万。所以增长里**至少 61% 是工具结果**。这是下限，因为上下文压缩一直在把旧结果截短。
- 18 件里有 9 件触发过上下文压缩（达到 8 万字符阈值），共 77 次。按压缩时记录的请求字符数配同轮输入 token，中位约 2.7 字符 / token（估算）。
- 只用来收集资料的轮次（只发搜索、读页这类只读调用）占全部轮次的 71%，占全部输入 token 的 69%。

### 机械往返

判定规则：一轮只发只读调用，且每个要读的 URL 都在之前的工具结果里出现过，例如逐个打开搜索结果里的链接，或者给同一页翻页。这种轮次里模型只是把上一步的结果搬进下一步。

- 机械往返有 49 轮，占全部轮次的 28%。
- 221 次读页里：翻页（带 offset）33 次，占 15%；重复读同一页同一段 16 次，占 7%，大多是上下文压缩后又读回来的。

## 2. PTC 上限收益估算

| | 保守 | 乐观 |
|---|---|---|
| 假设 | 只省机械往返；每省一轮，省下该任务的平均模型耗时和平均输入 token；工具照旧 | 每件任务的全部资料收集轮压成 1 轮；网页正文不进上下文（后续每轮输入回到「首轮 + 模型输出 + 2000」）；工具全部并行 |
| 省轮数 | 49 轮（28%） | 106 轮（61%） |
| 省模型耗时 | 225 秒（总耗时的 12%） | 554 秒（30%），另加工具并行约 12% |
| 省输入 token | 117 万（29%） | 281 万（69%） |

乐观档是上限：它假设代码里过滤一次就够，模型不需要看原文再决定下一步读什么。实际调研里，常常要读了第一批页面才知道下一步搜什么，所以真实收益落在两档之间。

还有两笔账要算进去：

- 写代码要额外的输出 token，见下面的原型。输出 token 比输入贵，也更慢。
- 只靠「工具并行执行」这一项（不让模型写代码），已经能拿到乐观档里「工具并行约 12%」那部分时间收益，而且不改模型行为。

## 3. 最小原型

本机临时脚本，复用产品里现成的 DeepSeek 搜索和读页类，只导入不修改。模型 DeepSeek flash，开思考（effort=medium，与产品执行层一致）。两个只读工具：`web_search`、`fetch_page`（每次 8000 字，和产品一致）。3 道真实风格的多步题：

1. 两种饮食模式各适合谁、有什么禁忌，各找 2 个权威来源；
2. 某编程语言新版本的发布日期和主要新特性，要官方来源；
3. 某数据库全文检索两种分词器在中文上的差别和限制，要官方文档出处。

对比两种做法：

- A 逐步调用：和产品一样，模型一轮一轮发工具调用，串行执行，结果原样进上下文，最多 14 轮。
- B PTC：模型一次写出一段 Python，用 `asyncio.gather` 并行调用两个工具，在代码里截取不超过 400 字的原文片段，只返回不超过约 6000 字的证据。代码出错就把报错交回模型改一次。最后模型凭证据写答案。

### 结果

A 每题跑 1 次，B 每题跑 2 次。

| 题 | 做法 | 模型轮数 | 输入 token | 输出 token | 总耗时 | 工具调用 |
|---|---|---|---|---|---|---|
| 1 | A | 14（到上限，未出答案） | 339,683 | 4,778 | 161 秒 | 26 |
| 1 | B | 2 / 3 | 2,927 / 3,522 | 6,192 / 4,720 | 58 / 38 秒 | 6 / 10 |
| 2 | A | 3 | 14,199 | 1,216 | 25 秒 | 4 |
| 2 | B | 2 / 2 | 1,753 / 1,223 | 2,007 / 1,357 | 25 / 15 秒 | 10 / 11 |
| 3 | A | 7 | 87,011 | 5,258 | 65 秒 | 10 |
| 3 | B | 2 / 2 | 1,833 / 1,624 | 11,108 / 6,264 | 63 / 48 秒 | 7 / 17 |

- **代码一次跑通：6 次里 5 次。** 唯一一次失败是把 `await` 写在了函数外，改一次就通。
- 轮数：多步题从 7～14 轮降到 2～3 轮；简单题从 3 轮降到 2 轮。
- 输入 token 降了 1～2 个数量级，因为网页正文不进上下文。
- 输出 token 反而变多，第 3 题多到 1.2～2.1 倍：写一段带过滤逻辑的代码比发几次工具调用长得多，开思考时更明显。所以简单题、中等题的总耗时基本没变（第 3 题 63 / 48 秒对 65 秒），只有像第 1 题那样逐步调用会拖到十几轮的题，PTC 才明显更快。
- 质量没有做盲评，只数了答案里的来源链接：B 的答案更短，链接更少（第 3 题 2～4 个，A 是 7 个）。原因是代码里的过滤规则是模型凭猜测事先写好的，筛掉了一部分有用的段落。要上线必须先做质量盲评。
- 原型的头三批运行因为我自己的沙箱写法有问题（没放开 import，不兼容 `asyncio.run` 写法，提示词被误改）全部失败。那些失败不是模型的问题，不计入结果。这也说明：自建 PTC 的主要工作量在执行环境，要能稳定接住模型的各种常见写法。

## 4. 推荐

**现在不做完整 PTC，先做两小块，按顺序来。**

1. **只读工具同一轮并行执行（先做）。** 模型已经有 45% 的轮次一轮发多个调用，现在却串行执行。改动面：`pi_bridge/bridge.mjs` 里只读工具（搜索、读页、读资料）的 `executionMode` 改成并行，`toolExecution` 改成 `'parallel'`；有副作用的工具保持串行（Pi 的规则是一批里只要有一个串行工具，整批就串行）；运行时要确认同一任务的多个工具调用并发写账本是安全的，搜索预算计数也要并发安全。预计省总耗时约 12%（自用库实测口径），不改模型行为，不增 token。
2. **一个「批量读页并摘取」的工具（第二步）。** 网页正文占工具结果的 86%，是上下文膨胀的主因。做一个工具：一次给多个 URL 加一个问题，工具内部并行读页，只返回和问题相关的原文片段，整页照旧缓存，验收引用时仍能核对原文。这能拿到 PTC 大部分的 token 收益（输入 token 估计省 29%～69% 的那部分），而且不用代码沙箱，不增加模型输出。片段怎么挑（关键词、向量还是交给一个便宜模型摘）要单独评测。
3. **完整 PTC 暂缓。** 原型证明了它可行（一次跑通率 5/6，轮数和输入 token 大降），但它要一个真正隔离的代码执行环境（子进程、限时、限内存、禁网、禁文件），每个内部调用都要照样记账本、扣搜索预算、能被取消。改动面大，而且输出 token 和耗时在中等题上不降反升，答案引用变少。前两步做完后再测一次，如果长调研任务的轮数仍然很多，再考虑。
