## 两层测法

1. **对照层（同一套脚本）**：`scripts/run-browser-check.py --mode compare`。同一个精简提示、同一个 deepseek-flash（思考关闭），一组用 Noyi 的浏览器工具（`personal_agent.browser` 的真实实现），一组用截图循环（动作后固定等 2 秒再截图，computer-use 参考实现的做法）。只比两种看网页的方式，不含 Noyi 自己的系统提示和上下文。
2. **整链路层**：`scripts/run-browser-check.py --mode e2e`。把任务当成用户的一句话交给 Noyi（接收层 → 执行层 → 加载浏览器能力包 → 交付验收），计交付和正确率。

两层都：每个站跑 5 次；浏览器在每组开始时启动一次（常驻）；模型请求遇到连接中断、超时、429、5xx 重试一次，重试计入耗时和 token；每次结果写一行到输出目录的 `results.jsonl`，跑一半中断可以从已有行数续跑。

## 门槛（全部要过）

| # | 门槛 | 在哪层测 | 怎么算 |
|---|---|---|---|
| G1 | 交付不少于 14/15 | 整链路 | 任务以「验收通过并送达」结束算交付 |
| G2 | 计数题和人工核对一致，错的不超过 1/5 | 整链路 | list 任务 5 次里，台数不是 4 或名字缺漏/多出的算错 |
| G3 | 输入 token 不超过截图组 | 对照层 | 每个站分别比：Noyi 浏览器组 5 次输入 token 中位数 ≤ 截图组 5 次中位数。三个站都要满足 |
| G4 | 每轮浏览器侧耗时 p50 ≤ 800 ms | 对照层和整链路都报，以整链路为准 | 每次 `browser_*` 工具调用里浏览器自己花的时间（动作 + 等稳定 + 取快照，含页面加载），所有调用的中位数 |
| G5 | 一次真实登录交接 | 人工 | 用户在手机上打开实时画面亲手登录，点「我登好了」或自动检测到登录完成后，任务自动接着做完并交付。Noyi 全程不经手密码。提前通知总控约用户 |

另外照实报告、不作门槛：每个任务的总耗时中位数、模型轮数、截图组同口径数字、交付里正确但答得啰嗦的情况。

### 第一次正式验收（2026-11-21，提交 56151a2，每站 5 次）

| # | 结果 | 是否过 |
|---|---|---|
| G1 | 整链路交付 12/15（search 2/5，form 5/5，list 5/5） | 未过 |
| G2 | list 5 次全对（4 台、名字齐） | 过 |
| G3 | 输入 token 中位数 Noyi / 截图：search 56.4K / 28.7K，form 9.0K / 49.1K，list 16.1K / 23.9K | 未过（search） |
| G4 | 整链路 50 次浏览器调用中位数 543 ms；对照层 search 1652、form 531、list 478 | 过（以整链路为准） |
| G5 | 未做 | — |

没过的原因（看了每次的记录）：
- G1：search 没交付的 3 次都卡在接收层。它把「查个版本号」判成只靠想就能回答的问题，交给了没有任何工具的作答路线，执行层只能报「做不到」。浏览器工具一次都没被调用。form 和 list 的说法带「填表」「翻页」，就没被这样判。
- G3：对照层 search 组有 11 次浏览器调用报 `Selector "body" does not match any element`。必应搜索页会自己跳转，取快照的那一刻新文档还没有 body，报错后模型只能换着网址重开，轮数和 token 都被抬高（5 次里有 4 次碰到）。截图组不读文档结构，所以不受影响。
- 对照层正确率：Noyi 组 search 4/5、form 5/5、list 4/5（不计入门槛），截图组 4/5、4/5、0/5。

### 第二次正式验收（2026-11-21，提交 f993fd0，Noyi 组 3 站各 5 次，截图组沿用第一次的数字）

第一次之后改了三处：作答路线声明需要工具时转成普通任务（ff26033），页面加载中途换文档时等新文档再取快照（25dd7f2），新窗口打开的链接改在任务标签页里打开（9f238b2）；另外预先备好一个空白标签页（f993fd0）。

| # | 结果 | 是否过 |
|---|---|---|
| G1 | 整链路交付 15/15 | 过 |
| G2 | list 5/5 全对 | 过 |
| G3 | 输入 token 中位数 Noyi / 截图：search 19.7K / 28.7K，form 10.2K / 49.1K，list 15.9K / 23.9K | 过 |
| G4 | 整链路 62 次浏览器调用中位数 1097 ms（search 1916、form 502、list 522） | 未过 |
| G5 | 未做 | — |

G4 没过的原因：第一次的 543 ms 里 search 只有 2 次真正用了浏览器，这次 5 次都用了，必应和 pypi.org 的调用把中位数抬了上去。search 的调用里，打开或跳转一次页面要 1.1～3.8 秒，其中网页自己加载（`pypi.org` 首次约 2 秒）和「等页面不再变化」（必应约 0.7～1.2 秒，上限 3 秒）是大头；取快照本身只要几十毫秒。

另外照实记录：search 第 2 次答错。作答路线没有调 report_unable，而是直接用 deliver_answer 回了「我没法打开网页」，所以没转成普通任务，但仍算交付。

### G4 门槛变更（2026-11-21，看过第二次结果之后改的）

- 原门槛：每轮浏览器侧耗时 p50 ≤ 800 ms，以整链路为准（含网页自己的加载时间）。第二次实测 1097 ms，未过。
- 改的原因（总控拍板）：800 ms 本来想卡的是 Noyi 自己的开销，网站本身加载慢不该算进去。
- 新门槛，两条都要过：
  - G4①：整链路三站合起来，每轮浏览器自身开销 p50 ≤ 800 ms。自身开销 = 浏览器侧总时间 − 网页自己的加载时间；网页自己的加载时间是主文档从发出请求到 load 事件的那一段，用浏览器的 Navigation Timing 测（一次调用里有多次加载就取时间段的并集）。
  - G4②：每个站的任务总耗时中位数都不超过截图组（截图组 search 34.3 s，form 57.8 s，list 28.2 s）。
- 原口径（含网页加载）的 p50 按站照实列出，不作门槛。

### 第三次正式验收（2026-11-21，提交 8a1b948，Noyi 组对照层和整链路 3 站各 5 次，截图组沿用第一次的数字）

第二次之后改了：作答路线的「需要外部信息」改成每次交付必填，选 false 的回答里不能说做不到（6308bd1）；取快照前等主文档加载完，再加 0.6 秒宽限接住必应加载后的自跳转，DOM 稳定的等待和它并行（8a1b948）；执行层提示「判断做不到之前先看能力包」（8a1b948）。

原口径（含网页加载）浏览器侧 p50，照实列出：整链路三站合计 959 ms；search 890、form 960、list 1316。对照层 search 1027、form 967、list 953。list 比第二次（522）高，主要是每次加载后多等的 0.6 秒宽限；这段宽限算在自身开销里。

回归：22 题难度评测（r1121c）均分 17.16（门槛 ≥17.0），首字中位数 0.85 s（≤1.1 s），回答里出现「已记录」之类账本字样 0 次。

实现期间的试跑（每站 1 次，不计入验收，只用来发现机制问题）：必应搜索结果页会自己跳转一次、上下文级请求拦截让必应返回空白页、表单 POST 在网络层中止会变错误页，三处都已在机制层改掉（见设计稿第 13 节）。改完后对照层 3 站各 1 次：Noyi 组 3/3 正确，输入 token 24.6K / 17.6K / 11.6K；截图组 2/3（翻页那次中途报错），67.8K / 35.8K / 50.9K。整链路 form 1 次：交付通过，1 次确认。
